## 二、参考实现全景

### 2.1 技术形态

| 维度 | 现状 |
|------|------|
| 语言 | Kotlin（KMP，`jvm("desktop")`，实质是单平台桌面项目） |
| UI | Compose Multiplatform + Material3 |
| 音频 | libmpv，通过 JNA 直接调 C API（无中间封装库） |
| 数据库 | SQLite JDBC，**手写 SQL，无 ORM** |
| 网络 | Ktor Client（OkHttp 引擎）+ kotlinx.serialization |
| RSS | 第三方库 `rssparser`，自己再做一层转换 |
| 图片 | Coil |
| 规模 | 57 个文件 / 15,413 行（不含测试约 14,300 行） |

### 2.2 分层与文件职责

原作者用的是"按功能包分包"，没有严格分层：

```
app/podara/
├── App.kt (2476)           ← 主窗口 + 首页 + 频道详情 + 侧边导航，全部塞在一起
├── Main.kt                 ← 入口、单例装配、崩溃日志
├── api/
│   ├── apple/              ← iTunes API 客户端（Search / Lookup / TopPodcasts）
│   ├── rss/                ← RSS 抓取（ETag/Last-Modified 条件请求）
│   └── model/              ← 跨源统一的 PodcastPreviewModel
├── data/
│   ├── AppDatabase.kt (1215)  ← 建表 + 12 个 DAO，全在这一个文件里
│   └── model/                 ← 12 个数据类
├── manager/                ← 业务编排：订阅、下载、导入导出、同步
├── player/
│   ├── MediaPlayerState.kt (539)  ← 全局播放状态 + 队列 + 会话恢复
│   ├── MpvAudioPlayerEngine.kt    ← libmpv 实现
│   ├── PlayerUI.kt (1748)         ← 全屏播放器 + 迷你播放器 + 队列抽屉
│   └── EpisodeProgress.kt         ← 收听进度（本 fork 新增）
├── screen/                 ← 发现(969) / 下载(1040) / 设置(835) / 历史(487) / 收藏(388)
├── component/              ← 复用组件：列表项、确认框、空状态
├── theme/                  ← DesignTokens(612) 设计变量 + Color + Theme
└── util/                   ← Strings(495) / Settings / 托盘 / 媒体键 / 日志
```

**读这份结构要先知道一件事**：`App.kt` 2476 行 + `PlayerUI.kt` 1748 行 = 全项目 27%
的代码在两个文件里。这是原作者最大的技术债，也是重写时最该改的地方。

### 2.3 数据层：12 张表

原作者的设计意图很清晰——**一切都落库，重启不丢任何状态**。

| 表 | 作用 | 设计要点 |
|----|------|----------|
| `podcast` | 播客元数据 | `origin`（RSS URL）是主键，天然去重 |
| `podcastEpisode` | 单集 | `guid` 唯一，`isNew` 标记未读，`pubDate` 索引排序 |
| `podcastEpisodePlayState` | 播放状态 | 原本只有 `state/played` 且从不写入；本 fork 补了 `positionMs/durationMs/finished` |
| `podcastHistory` | 收听历史 | 带 `historyId`，支持"听了两次"的记录 |
| `podcastFavorite` | 收藏 | 独立表而非布尔字段，便于按收藏时间排序 |
| `podcastSubscription` | 订阅 | 存 `cacheETag/cacheLastModified/cacheContentLength` 做增量抓取；`enableNotifications/enableAutoDownload` 是**死字段**（无 UI 无逻辑） |
| `podcastDownload` / `downloadTask` | 下载记录与任务 | 两表分离：一个记已完成，一个记进行中/暂停，支持断点续传 |
| `podcastItunesLookup` | iTunes ID → RSS 映射 | 解决"榜单里是 iTunes ID、订阅需要 RSS URL"的转换，缓存避免重复请求 |
| `playerSession` | 会话恢复 | 队列位置、播放位置、倍速、音量，单行表（id=1） |
| `playerQueueItem` | 队列持久化 | 重启后播放列表还在 |
| `syncAction` | 待同步动作 | 为跨设备同步预留，实际没接 UI |

**可借鉴**：这套表结构基本够用，重写时按此设计能省一周。
**要改的**：`ALTER TABLE` 幂等迁移散落在建表代码里，重写应上正式迁移版本管理（如 Flyway / SQLDelight schema）。

### 2.4 播放内核

原作者做了一件正确的事：**先抽接口，再实现**。

```kotlin
interface AudioPlayerEngine {
    val isPlaying: Boolean
    val currentPosition: Long
    val duration: Long
    val playbackState: PlaybackState   // IDLE/LOADING/PLAYING/PAUSED/STOPPED/ERROR
    fun play(url, speed, startPositionMs, durationMs)
    fun pause(); fun resume(); fun stop()
    fun seek(ms); fun setSpeed(f); fun setVolume(v); fun release()
    var onPlayStateChanged: ((Boolean) -> Unit)?
    var onPositionChanged: ((Long, Long) -> Unit)?
    var onError: ((String) -> Unit)?
}
```

`MpvAudioPlayerEngine` 用 JNA 直连 libmpv，只用了 9 个 C 函数
（`mpv_create` / `mpv_initialize` / `mpv_command` / `mpv_set_property_string` /
`mpv_observe_property` / `mpv_wait_event` / `mpv_request_log_messages` 等），
事件循环在独立线程里跑 `mpv_wait_event`。

**为什么选 libmpv**：格式通吃、支持变速不变调、跨平台一致。
**代价**：要随包分发 `libmpv-2.dll`（约 20MB），且 JNA 绑定的坑不少
（本项目踩过的：`WPARAM` 必须按指针宽度取整）。

**重写建议**：保留接口设计，换实现。
- Windows 优先：`NAudio` / `Media Foundation`（系统自带，零分发体积，但格式支持弱于 mpv）
- 跨平台：继续 libmpv，或 `miniaudio`（C 单文件，需要自己写解码）
- 若用 Flutter：`media_kit`（就是 libmpv 封装）或 `just_audio`

### 2.5 内容获取链路

```
发现页
  ├─ 榜单：GET itunes.apple.com/{CN|US}/rss/toppodcasts/limit=50/explicit=true/json
  ├─ 搜索：GET itunes.apple.com/search?media=podcast&country=US&term=...
  └─ 解析：GET itunes.apple.com/lookup?id=1,2,3&media=podcast  → 批量拿 feedUrl
                                                              → 落库 podcastItunesLookup
订阅后
  └─ GET <feedUrl>  (带 If-None-Match / If-Modified-Since)
       → rssparser 解析 → RssConverter 转成 Podcast/PodcastEpisode → 入库
```

**原作者的三个设计值得抄**：

1. **统一预览模型**：无论榜单还是搜索，都转成 `PodcastPreviewModel`，UI 只认这一个类型。多源接入时这层抽象很值钱。
2. **条件请求**：订阅表里存 ETag/Last-Modified/Content-Length，命中 304 就不解析，省流量省 CPU。
3. **ID→RSS 映射缓存**：iTunes 榜单给的是数字 ID，订阅需要 RSS URL，每次转换都要请求一次 lookup；缓存后只在首次付出这个成本。

**两个坑**：

- `Search.search()` 的 `countryCode` 默认 `"US"`，而 `DiscoverScreen` 调用时**没传**，所以中文关键词实际是在美国区搜。榜单那边传了 `CN`，两边不一致。**这是一行就能修的 bug。**
- 苹果的 `rss/toppodcasts` 是老 Marketing 接口，官方多年不更新文档，见过区域返回空。**不能当唯一数据源**。

### 2.6 订阅更新策略（这块设计得不错）

- 进入「最新更新」页触发，**10 分钟节流**（`HOME_AUTO_REFRESH_INTERVAL_MS`）
- 并发 **3**（`Semaphore(3)`），避免同时打十几个 RSS 被限流
- 首次抓取某频道时当作**基线**，不把全部历史标成未读（本 fork 加的判断）
- 新节目写 `isNew=1`，播放后清标记

**可借鉴**：节流 + 并发上限 + 首次基线，这三点是踩过坑才知道的细节，直接照搬。

### 2.7 下载

- `HttpURLConnection` + `Range: bytes=N-` 断点续传
- 服务端不支持 Range（返回 200 而非 206）时**自动重下**，不写坏文件
- `RateLimiter` 令牌桶做限速（`speedLimitKbps`，0 = 不限）
- 任务状态机：pending → downloading → paused / completed / failed

**评价**：实现朴实但完整，暂停/续传/限速/重试都有。重写时用 OkHttp 的 `Range` + 协程会更简洁。

### 2.8 UI 与设计系统

- `DesignTokens.kt`（612 行）：spacing / radius / 字号 / 动效时长 / 颜色，全部集中定义
- `Strings.kt`（495 行）：`Map<String, String>` 两套（en/zh），`Strings["key"]` 取值
- 主题：跟随系统的深浅色 + 每档播客从封面提取主题色（`imageSeedColor`）

**可借鉴**：DesignTokens 集中管理是对的，避免硬编码 dp。
**要改的**：`Strings` 用 map 取值**编译期不校验**，写错 key 只会显示成 key 本身。重写用资源系统或类型安全的 key 常量（更好的做法是生成代码）。

### 2.9 系统集成

| 能力 | 实现思路 |
|------|----------|
| 系统媒体键 | JNA `WH_KEYBOARD_LL` 全局钩子，独立线程跑 `GetMessage` 循环，命中返回 1 吞掉事件；长按 350ms 去抖 |
| 系统托盘 | AWT `TrayIcon`，右键菜单（显示/隐藏/播放/暂停/上下集/退出） |
| 关闭行为 | 三选一（退出 / 最小化到托盘 / 每次询问），选择可记忆 |
| 单实例 | 未实现（可多开，会同时写同一个 SQLite） |
| 崩溃日志 | `~/.podara/crash.log` |

**媒体键的坑（重写必须知道）**：
`WPARAM` 在 64 位下是按指针宽度传的整数，必须 `Pointer.nativeValue(wParam)` 取值；
用 `getInt(0)` 会把它当地址解引用 → 回调抛异常 → 事件被静默丢弃。

### 2.11 原作者做法的得与失

**值得继承的判断**：

1. 播放器先抽接口再实现（换引擎成本低）
2. 一切状态落库，重启零丢失（用户对播客客户端的核心期待）
3. 统一预览模型，多源接入只改 adapter
4. 条件请求 + 并发上限 + 刷新节流，这三个是"不被打限流"的关键
5. DesignTokens 集中管理样式

**必须改掉的**：

1. **巨型文件**：`App.kt` 2476 行、`PlayerUI.kt` 1748 行。重写应按"页面 = 一个文件、一块 UI = 一个组件"拆
2. **无 ORM + 手写 SQL 分散**：1215 行数据库文件里混了建表、迁移、12 个 DAO
3. **String map 无类型校验**：写错 key 不报错
4. **无单实例保护**：多开会抢同一个 SQLite
5. **死字段**：`enableNotifications` / `enableAutoDownload` 建了字段没实现，容易误导后续维护

## 四、技术选型对比

### 4.1 UI 与语言

| 方案 | 优势 | 劣势 | 适配度 |
|------|------|------|--------|
| **Kotlin + Compose Multiplatform** | 与参考实现同栈，迁移知识零损耗；一套 UI 可扩到 Android/iOS | 桌面打包是硬伤（本机 `jpackage` 因缺 jmods 直接失败）；桌面生态小 | ★★★★ |
| **Flutter** | 跨平台最成熟；音频插件生态好（`just_audio`/`media_kit`）；打包一条命令 | Dart 要重新学；桌面端系统集成需写平台通道 | ★★★★ |
| **Tauri + React** | 包体小；Web 技术栈人才多；Rust 后端性能好 | 长列表性能要调；音频要走 Rust 或 HTML5 audio；系统集成靠插件 | ★★★ |
| **Avalonia (.NET)** | Windows 体验最好；打包成熟；C# 生态 | 移动端弱；需要 .NET 经验 | ★★★（若只做 Windows 则 ★★★★★） |
| **WPF / WinUI3** | 原生 Windows，控件最贴系统 | 只能 Windows | ★★（无跨平台打算则 ★★★★） |

**结论**：取决于平台范围——
- 只做 Windows，追求省事：**Avalonia**
- Windows + 未来移动端，且愿学新语言：**Flutter**
- 想复用现有 Kotlin 认知 + 接受打包折腾：**Compose Multiplatform**

### 4.2 音频

| 方案 | 优势 | 劣势 |
|------|------|------|
| libmpv（现有） | 格式通吃、变速不变调、跨平台一致 | 分发 20MB DLL；JNA 绑定坑多 |
| NAudio / Media Foundation | Windows 自带，零分发 | 格式支持弱，变速要自己做 |
| miniaudio | 单文件 C，轻 | 解码要自己接，工作量大 |
| media_kit（Flutter） | libmpv 封装，开箱即用 | 仍是 libmpv 体积 |

**结论**：播客只需要 MP3/AAC/M4A/OGG + 变速。**不要过度设计**——
Windows 优先就用 Media Foundation/NAudio；要跨平台就用 libmpv，但**别自己写 JNA 绑定**，
选现成库（Flutter 的 media_kit、Rust 的 libmpv-rs）。

### 4.3 数据存储

| 方案 | 说明 |
|------|------|
| SQLite + ORM（Exposed / SQLDelight / Drift / EF Core） | **推荐**。表结构和参考实现一致，但用 ORM 消灭手写 SQL 分散问题 |
| Realm / ObjectBox | 省事，但迁移和复杂查询受限 |
| JSON 文件 | 只适合设置，不适合 12 张表 |

**结论**：SQLite + 带迁移管理的 ORM。参考实现的 12 张表可以直接照抄设计。

### 4.4 定稿结论（2026-10-27 对齐后）

已确认前提：**Windows 优先、预留 macOS**、**开源**、
**要求轻量化 + 低资源占用 + 现代审美**。

按这三条收敛，结论是 **Tauri 2 + Svelte 5 + Rust + SQLite**：

| 指标 | Compose Desktop（现状） | Flutter | **Tauri 2（选它）** |
|------|------------------------|---------|---------------------|
| 空闲内存 | **实测 426 MB** | 100–150 MB | **80–120 MB** |
| 安装包 | 打包未成功（缺 jmods） | 15–25 MB | **8–15 MB** |
| 冷启动 | 2–3 s | 1–2 s | **< 1.5 s** |
| UI 审美上限 | 中（Material 味重） | 中高（自绘） | **最高（Web 生态）** |
| 系统集成 | 手写 JNA | 写平台通道 | **官方插件（托盘/快捷键/通知）** |
| 学新语言 | 不用 | Dart | Rust（后端逻辑量小） |

排除理由：

- **Compose Desktop 排除**：JVM 堆是硬成本，实测 426MB 内存，且本机打包已失败过一次，
  与"轻量化"直接冲突。
- **Electron 排除**：同为 Web 技术，但自带整个 Chromium，包体 80MB+、内存 200MB+。
  Tauri 用系统 WebView2，UI 能力相同，体积和内存低一个量级。
- **Flutter 保留为备选**：若发现 WebView 在音频或长列表上有硬伤，作为退路。

**Tauri 的关键取舍**：UI 跑在 WebView2 里，重活（网络、解析、数据库、下载、音频控制）
全在 Rust 侧。既有 Web 的审美灵活性，又不把浏览器当后端用。

细化设计见 `docs/技术设计细化.md`。

## 五、新仓库模块划分建议

以"换 UI 框架也不动核心"为目标分层：

```
core/
  ├─ model/            数据模型（Podcast / Episode / PlayState / Queue...）
  ├─ playback/         PlayerEngine 接口 + 队列状态机 + 进度计算
  ├─ content/          PodcastSource 接口（多源适配）
  │   ├─ apple/        iTunes 实现
  │   ├─ podcastindex/ Podcast Index 实现
  │   └─ rss/          RSS 直抓实现
  └─ sync/             同步接口（先留空实现）
data/
  ├─ db/               ORM 实体 + 迁移
  └─ repository/       仓储层（订阅/历史/收藏/下载/进度）
app/                   应用层：用例（UseCase）+ 状态管理
ui/                    表现层：页面、组件、主题、文案资源
platform/              平台特性：媒体键、托盘、通知、文件对话框
```

**关键约束**（用来防止重蹈覆辙）：

1. 单文件不超过 400 行，超过就拆
2. UI 层不允许直接写 SQL
3. 平台特性必须走接口，核心不 import 平台 API
4. 文案必须类型安全（资源文件或生成的常量），不允许裸字符串 key

## 八、分支与工程规范

参考实现所在的仓库已经按单一职责整理完毕（详见同目录下的分支说明）：

| 分支 | 定位 | 边界 |
|------|------|------|
| `main` | 上游镜像 | 只跟随 `upstream/main`，不提交自己的改动 |
| `develop` | 集成主线 | 所有功能分支合入这里，唯一可发布分支 |
| `feat/system-media-keys` | 媒体键 | 只碰媒体键相关文件 |
| `feat/player-queue-manual` | 队列手动化 | 只碰播放队列逻辑 |
| `feat/subscriptions-latest-updates` | 订阅页聚合 | 只碰首页与订阅刷新 |
| `feat/episode-progress` | 收听进度 | 基于订阅页分支（有代码依赖） |
| `docs/fork-notes` / `docs/new-repo-plan` | 文档 | 只碰 md |
| `chore/dev-launcher` | 本机构建辅助 | 只碰 `scripts/` |

**新仓库沿用同一套规则**：

1. `main` 永远可发布，`develop` 集成，功能一律走 `feat/*`
2. 一个分支只做一件事，分支名要说清做什么
3. 有依赖的功能用堆叠分支（`feat/b` 基于 `feat/a`），不要混在一个分支里
4. 合并用 `--no-ff`，保留功能边界
5. 文档、脚本各走独立分支，不夹在功能提交里

## 九、Agent 平台与模型选型

### 9.1 这个项目的任务特征

先看要干的活长什么样，再谈工具：

| 特征 | 具体表现 | 对工具的诉求 |
|------|----------|--------------|
| 代码量大 | 目标 10k+ 行，20+ 模块 | 长上下文、能跨文件协同改 |
| 反馈慢 | 一次 Gradle 编译 30–60 秒 | 能跑命令、读输出、自己修错 |
| 强类型 | Kotlin/Dart/Rust，编译期就能抓错 | 每步都要编译验证 |
| 长期迭代 | 3–5 个月，几十个功能点 | 记忆/规范能沉淀，不是一次性对话 |
| 中文协作 | 需求、文档、报错都要中文 | 中文表达质量 |
| 单人开发 | 预算敏感 | 成本可控 |

### 9.2 候选方案对比

| 方案 | 优势 | 劣势 | 本项目适配 |
|------|------|------|------------|
| **WorkBuddy（当前）** | 中文原生；能跑命令、改文件、读构建输出；有技能/记忆/钩子体系；模型可配；已在你这台机器上验证过能编译、能跑起 GUI | 深度重构的"一口气写完"能力弱于顶级模型；长任务需要人工分段 | ★★★★★ |
| **Codex CLI** | 终端 agent，重构与机械改动强；沙箱模式清晰；支持子 agent 与 MCP；读构建报错自己修的闭环好 | **模型锁定 OpenAI**；无 diff 视图（大改动审阅累）；国内网络与账号门槛；会话间记忆不连续 | ★★★★ |
| **CodeBuddy（腾讯）** | 中文、国内网络友好、IDE 集成好 | 长链路自主执行较弱，偏"辅助编码" | ★★★ |
| **Claude Code** | 公认多文件重构质量最好，中途纠偏能力强 | 需 Anthropic 账号；成本最高 | ★★★★（作为攻坚辅助） |
| **本地模型（Ollama + 编码模型）** | 零边际成本、代码不出本机 | 大仓重构容易丢线索，上下文吃紧 | ★★（只适合小任务） |

### 9.3 结论

**主用 WorkBuddy，不整体切换到 Codex。**

理由：

1. 这个项目的瓶颈**不是"一次写多少代码"，而是"每次改完能不能编译过、能不能跑起来"**。
   已验证 WorkBuddy 在这台机器上能执行 Gradle 构建、能启动 GUI 做冒烟验证——
   这个闭环比模型分数更值钱。
2. 任务周期 3–5 个月、需要沉淀规范（编码约定、踩坑记录、模块边界），
   这正好是"有记忆体系 + 项目级规范文件"的工具更擅长的事。
3. 中文需求对齐、文档产出占工作量不小，中文原生工具省沟通成本。
4. Codex 的模型锁定 + 无 diff 视图，对"大改动要人审"的场景反而更累。

**Codex 的正确用法是"补位"，不是"替代"**：

- 适合它：机械重构（批量重命名、统一日志、替换废弃 API）、跑测试修失败、跨文件一致性改动
- 不适合它：需要产品判断的架构决策、需要反复和你对齐需求的探索

### 9.4 Harness 配置建议

不管用哪个工具，这套配置都该有（放在仓库根，让 agent 每次都能读到）：

**1. 项目规范文件（`AGENTS.md` / 项目级规则）**

必须写进去的内容：

```markdown
## 构建与验证
- 编译：<命令>            # 每次改完必须跑
- 单测：<命令>
- 冒烟：<启动方式>

## 代码规范
- 单文件不超过 400 行
- UI 层禁止直接写 SQL
- 平台 API 必须走接口
- 文案禁止裸字符串 key

## 边界
- 不要动 <目录>（生成的、第三方的）
- 不要改 public API 签名，除非明确要求

## 提交
- 每完成一个可编译的步骤就提交一次
- 提交信息格式：<type>(<scope>): <中文描述>
```

**2. 强制验证闭环**

每次让 agent 改代码，流程固定为：改 → 编译 → 失败就修 → 编译过 → 提交。
**没有编译通过的改动不许提交**。这一条能挡掉 80% 的返工。

**3. 小步提交**

每个功能点一个提交，出错能精确回滚。参考这次的教训：
手工解冲突一旦出错，没有小步提交就得整体重来。

**4. 只读/可写边界**

明确告诉 agent 哪些目录不许碰（`build/`、`libs/`、`.gradle/`、第三方源码）。
这次的 `stash` 误删 `docs/` 就是边界不清导致的。

**5. 定期同步规范文件**

踩过的坑要沉淀进去（比如"bat 必须 CRLF"、"`sub` 是 VBS 保留字"），
否则每换一个会话就会重踩一次。

### 9.5 推荐的模型分层

| 任务类型 | 模型档位 | 说明 |
|----------|----------|------|
| 架构设计、模块拆分、方案评审 | 最强推理档 | 一个月用几次，值得花钱 |
| 日常功能实现（写页面、写 DAO、接 API） | 中等偏强 | 主力，占 70% 的 token |
| 机械改动（重命名、格式化、批量替换） | 轻量快模型 | 便宜、够用 |
| 跑测试修失败 | 中等 | 需要能读报错并定位 |

**不建议全程用最贵的模型**——重构期的 token 消耗会失控，且边际收益递减。

### 9.6 一句话总结

> 用 **WorkBuddy 做主力**（中文协作 + 能验证构建 + 规范沉淀），
> 模型按任务分层（架构用最强、实现用中等、机械活用量轻），
> **Codex 作为机械重构和批量改动的补位工具**，
> **Claude Code 留给"卡住了"的攻坚场景**。
> 不要为了"工具更酷"而切换，这个项目的胜负手是**每次改动都能编译通过并跑起来**。
