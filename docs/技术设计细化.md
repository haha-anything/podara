# 技术设计细化（Tauri 方案）

> 基于 `新仓库开发方案.md` 第 4.4 节的定稿结论展开。
> 前提：Windows 优先 + 预留 macOS、开源、轻量化 + 现代审美。
> 这份文档的目标是「照着它就能开工」，不含代码实现。

---

## 一、技术栈定稿

| 层 | 选型 | 说明 |
|----|------|------|
| 应用壳 | **Tauri 2** | 用系统 WebView2，不自带浏览器 |
| 前端框架 | **Svelte 5** | 运行时几 KB，比 React 轻一个量级；runes 状态模型够用 |
| 构建 | **Vite 6** | 冷启动构建快 |
| 样式 | **Tailwind CSS 4** | 编译期生成，运行时零开销 |
| 语言（前端） | TypeScript | — |
| 语言（后端） | Rust（stable） | 网络、解析、DB、下载、系统集成 |
| 数据库 | **SQLite** + `rusqlite` | 单文件、零配置、可控 |
| 迁移 | 自建 `schema_version` 表 | 简单场景不必上 diesel/sqlx migrate |
| 异步运行时 | `tokio` | reqwest 依赖它 |
| HTTP | `reqwest`（rustls） | 比 openssl 省依赖、编译快 |
| RSS 解析 | `feed-rs` | 处理 RSS/Atom/命名空间 |
| 序列化 | `serde` / `serde_json` | — |
| 日志 | `tracing` + 文件轮转 | — |
| 错误 | `thiserror`（库）+ `anyhow`（应用层） | — |
| 测试 | `cargo test` + `vitest` | — |

**刻意不引入的东西**（为了轻量）：

- 不要 ORM（diesel/sea-orm）——12 张表手写 SQL 完全可控，且避免编译期膨胀
- 不要 UI 组件大礼包（MUI/Ant）——手写 + Tailwind，样式才跟得上审美要求
- 不要状态管理库（Redux/Zustand）——Svelte 5 的 runes 原生够用
- 不要动画库（Framer Motion 等）——Svelte 内置 transition 足够且更轻

## 二、进程架构

```
┌─────────────────────────────────────────┐
│  WebView2（Svelte UI，负责渲染与交互）    │
│  · 页面、组件、动画                      │
│  · <audio> 元素持有播放状态              │
└──────────────┬──────────────────────────┘
               │ IPC：invoke（前端调用）+ emit（后端推送）
┌──────────────┴──────────────────────────┐
│  Rust Core（负责一切"重活"）             │
│  · reqwest 抓 RSS / 调 API               │
│  · feed-rs 解析                          │
│  · SQLite 读写                           │
│  · 下载（断点续传、限速）                 │
│  · 托盘 / 全局媒体键 / 通知 / 单实例      │
└─────────────────────────────────────────┘
```

**职责边界（硬约束）**：

| 事情 | 谁做 | 为什么 |
|------|------|--------|
| 抓 RSS、解析 XML | Rust | 大文件、CPU 密集，别放 WebView |
| 所有 SQL | Rust | 前端不许碰数据库 |
| 下载与限速 | Rust | 需要精确控制并发与限速 |
| 播放控制、进度 | **前端 `<audio>`** | 与 UI 天然同步，省一层 IPC 延迟 |
| 进度落库 | 前端节流后 invoke → Rust | 避免每次 timeupdate 都跨进程 |
| 全局媒体键 | Rust 监听 → emit 给前端 | 前端执行实际播放控制 |

### 2.1 IPC 接口草案

**前端 → 后端（commands）**

```
feed_subscribe(url)                → Podcast
feed_unsubscribe(origin)           → ()
feed_refresh(origin)               → RefreshResult { new_episodes, not_modified }
feed_list()                        → Podcast[]
episode_list(origin, offset, limit)→ Episode[]

discover_top(country, limit)       → PodcastPreview[]
discover_search(query, country)    → PodcastPreview[]
discover_genres()                  → Genre[]

progress_save(episode_id, pos, dur)→ ()
progress_get(episode_id)           → PlayState?
progress_list_recent(limit)        → PlayState[]

download_start(episode_id)         → ()
download_pause(episode_id)         → ()
download_cancel(episode_id)        → ()

session_save(state)                → ()
session_load()                     → PlayerSession?
settings_get()/settings_set(...)   → ()
```

**后端 → 前端（events）**

```
download-progress  { episode_id, received, total, speed }
download-done      { episode_id }
download-failed    { episode_id, message }
listen-progress    { received, total }        # 订阅刷新进度
media-key          { action: "play"|"next"|"prev"|"stop" }
tray-action        { action }
```

## 三、音频方案（最容易翻车的地方）

### 3.1 主方案：HTML5 `<audio>`

WebView2 就是 Chromium，`<audio>` 支持的正是播客常用格式：
MP3、AAC/M4A、OGG/Opus、FLAC、WAV。

**能满足的需求**：

| 需求 | 实现 |
|------|------|
| 播放/暂停/seek | 原生 |
| 倍速 0.5–3.0，变速不变调 | `audio.playbackRate`（Chromium 内置时间伸缩） |
| 音量 | `audio.volume` |
| 进度事件 | `timeupdate`（约 4Hz，够用） |
| 睡眠定时 | `setTimeout` + `pause()` |
| 章节跳转 | `audio.currentTime = chapter.start` |
| 音量增强（>100%） | **WebAudio**：`createMediaElementSource` + `GainNode` |

**要求服务器支持 Range**：播客 CDN 基本都支持，否则 seek 会重下整个文件。
降级：检测到不支持就整集下载到本地再播。

### 3.2 三个必须提前处理的问题

**问题一：后台定时器被节流。**
WebView2 在窗口隐藏时会节流 JS 定时器（可能降到 1 次/秒甚至更低）。
- 播放本身不受影响（有音频输出时 Chromium 不会挂起）
- 但 `setTimeout` 驱动的进度上报会变慢
- **对策**：进度上报挂在 `timeupdate` 事件上（事件驱动不受定时器节流影响），
  再用 Rust 侧的定时器做兜底（每 5 秒向库里 flush 一次）

**问题二：窗口隐藏后音频可能被中断。**
最小化到托盘时如果用 `window.close()` 会销毁 WebView。
- **对策**：托盘最小化要用 `window.hide()`，不要 destory；退出才销毁

**问题三：格式兼容的边缘情况。**
个别播客用 ALAC、或者 MP3 里塞了奇怪的 ID3。
- **对策**：预留 `PlaybackBackend` 接口，Rust 侧可接 `symphonia + cpal` 兜底（V2 再做）

### 3.3 为什么不自己写音频引擎

参考实现自己写了 libmpv 的 JNA 绑定，代价是：
20MB DLL、一堆 FFI 坑（`WPARAM` 宽度问题就调了很久）、跨平台要各带一份。

播客只需要"能播 + 能变速"，Chromium 已经做得很好。
**把自研精力花在推荐、章节解析、同步上，比花在解码器上划算得多。**

## 四、数据层

### 4.1 迁移策略

```sql
CREATE TABLE schema_version (version INTEGER PRIMARY KEY, applied_at INTEGER);
```

启动时读版本号，按顺序执行 `migrations/001_init.sql`、`002_add_xxx.sql`。
比在代码里散落 `ALTER TABLE` 干净（参考实现就是散落的，难维护）。

### 4.2 核心表 DDL 草案

```sql
-- 播客
CREATE TABLE podcast (
  origin        TEXT PRIMARY KEY,      -- RSS URL，天然去重
  title         TEXT NOT NULL,
  author        TEXT,
  description   TEXT,
  image_url     TEXT,
  link          TEXT,
  language      TEXT,
  seed_color    INTEGER,               -- 封面取色
  source        TEXT DEFAULT 'rss',    -- rss / apple / podcastindex
  created_at    INTEGER NOT NULL
);

-- 单集
CREATE TABLE episode (
  id            TEXT PRIMARY KEY,      -- 优先 guid，兜底 url 的 hash
  origin        TEXT NOT NULL REFERENCES podcast(origin) ON DELETE CASCADE,
  title         TEXT NOT NULL,
  description   TEXT,
  audio_url     TEXT NOT NULL,
  image_url     TEXT,
  pub_date      INTEGER NOT NULL,
  duration_ms   INTEGER DEFAULT 0,
  is_new        INTEGER DEFAULT 0,
  chapters_url  TEXT,                  -- <podcast:chapters>
  transcript_url TEXT                  -- <podcast:transcript>
);
CREATE INDEX idx_episode_origin_pub ON episode(origin, pub_date DESC);
CREATE INDEX idx_episode_new ON episode(is_new) WHERE is_new = 1;

-- 播放进度（参考实现的关键改进，直接继承）
CREATE TABLE play_state (
  episode_id    TEXT PRIMARY KEY REFERENCES episode(id) ON DELETE CASCADE,
  position_ms   INTEGER NOT NULL DEFAULT 0,
  duration_ms   INTEGER NOT NULL DEFAULT 0,
  finished      INTEGER NOT NULL DEFAULT 0,   -- 粘性：>98% 置 1，永不回退
  updated_at    INTEGER NOT NULL
);

-- 订阅（含增量抓取缓存）
CREATE TABLE subscription (
  origin         TEXT PRIMARY KEY,
  notify_new     INTEGER DEFAULT 1,     -- 这次是真的要实现
  auto_download  INTEGER DEFAULT 0,
  etag           TEXT DEFAULT '',
  last_modified  TEXT DEFAULT '',
  content_length TEXT DEFAULT '',
  last_checked   INTEGER DEFAULT 0,
  new_count      INTEGER DEFAULT 0
);

-- 下载任务
CREATE TABLE download_task (
  episode_id    TEXT PRIMARY KEY,
  origin        TEXT NOT NULL,
  file_path     TEXT,
  received      INTEGER DEFAULT 0,
  total         INTEGER DEFAULT 0,
  status        TEXT NOT NULL,          -- pending/downloading/paused/done/failed
  error         TEXT,
  updated_at    INTEGER NOT NULL
);

-- 播放会话（重启恢复）
CREATE TABLE player_session (
  id              INTEGER PRIMARY KEY CHECK (id = 1),
  current_episode TEXT,
  position_ms     INTEGER DEFAULT 0,
  speed           REAL DEFAULT 1.0,
  volume          INTEGER DEFAULT 100,
  updated_at      INTEGER
);

-- 播放队列（顺序即 id 顺序）
CREATE TABLE queue_item (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  episode_id  TEXT NOT NULL,
  added_at    INTEGER NOT NULL
);
```

**评价参考实现的表设计**：12 张表基本够用，上面是精简版。
`podcastHistory` / `podcastFavorite` 可以先用 `episode` 上的字段实现，
真需要"听了几次"的历史记录时再拆表（YAGNI）。

### 4.3 数据库位置

```
%APPDATA%/你的App/podara.db        # Windows
~/Library/Application Support/你的App/podara.db   # macOS
```

用 Tauri 的 `app_data_dir()`，不要写死路径。

## 六、关键流程

### 6.1 订阅刷新（并发控制是重点）

```
前端触发 refresh
  → Rust: 读 subscription 表，筛出 last_checked 超过 10 分钟的
  → 用 Semaphore(3) 限制并发，逐个：
      GET feedUrl
        If-None-Match: <etag>
        If-Modified-Since: <last_modified>
      ├─ 304 → 跳过（不解析，省 CPU）
      └─ 200 → feed-rs 解析 → 与库中 guid 比对 → 新集 is_new=1
                → 更新 etag/last_modified/last_checked
  → emit listen-progress 推进度
  → 返回 { new_episodes, not_modified }
```

**首次抓取特殊处理**：库里没有该 origin 的任何单集时，全部入库但 **is_new=0**
（当作基线，避免一次冒出几百条未读）。这一条是参考实现踩坑后才加的。

### 6.2 播放与进度

```
用户点某集
  → 前端: audio.src = url; audio.playbackRate = 用户设置; audio.play()
  → 前端: 从 progress_get 拿到 position，audio.currentTime = position
  → audio.ontimeupdate（约 4Hz）
      → 更新 UI 进度条（纯前端，无 IPC）
      → 每 5 秒节流一次：progress_save(episode_id, pos, dur)
  → 暂停/切集/退出：立即 flush 一次

finished 判定：
  前端计算 pos/dur > 0.98 → invoke progress_finish(episode_id)
  → Rust 置 finished=1（粘性，重听也不回退）
```

**为什么 finished 要粘性**：用户听完一集后再重听，不该被打回"未听完"。
参考实现已经这么做了（`EpisodeProgress.finished` 一旦置位不再清除）。

### 6.3 下载

```
download_start(episode_id)
  → Rust: 建 download_task(status=pending)
  → 检查是否有断点（task.received > 0）
  → GET Range: bytes=<received>-
      ├─ 206 → 追加写入
      └─ 200 → 服务端不支持续传，删文件重下
  → 流式写入 + 令牌桶限速（用 tokio 的 interval 控制节奏）
  → 每 500ms emit download-progress
  → 完成：改文件名为最终名，status=done，写 play_state 的本地路径
```

## 七、UI 设计方向

### 7.1 布局

```
┌────────┬──────────────────────────────────┐
│        │  ┌─ 顶栏：标题 / 搜索 / 排序 ─┐    │
│ 侧边栏  │  │                            │    │
│ 导航    │  │  主内容区（列表 / 网格）    │    │
│        │  └────────────────────────────┘    │
├────────┴──────────────────────────────────┤
│  播放条：封面 标题/作者  进度  控制  音量 队列 │
└───────────────────────────────────────────┘
```

- 侧边栏：图标 + 文字，可折叠为纯图标（宽度 220px ↔ 64px）
- 播放条：固定 72px 高，未播放时隐藏
- 队列：右侧抽屉（不是独立页），从播放条展开

### 7.2 视觉

| 项 | 取值 |
|----|------|
| 主色 | 跟随播客封面取色（参考实现已验证这个思路） |
| 背景 | 深色优先，`#0E0E10` 系 |
| 卡片圆角 | 12px（列表项）/ 16px（大卡） |
| 字体 | 系统栈：`Segoe UI Variable, -apple-system, sans-serif` |
| 层级 | 用阴影 + 1px 描边区分，不要重投影 |
| 封面 | 大卡用模糊封面做背景（blur 40px + 低透明度） |

### 7.3 动效（克制）

- 列表项进入：stagger 30ms，`fly + fade`，200ms
- 播放条展开为全屏播放器：共享元素过渡 300ms
- 进度条：数值变化用 `transition: width 100ms linear`（跟手）
- 不要做：过度弹跳、超过 300ms 的过渡、同时动三个以上元素

### 7.4 信息密度

参考小宇宙：**列表一行要能看到** 标题、作者、时长、发布时间、收听进度。
参考实现的教训是状态标签 + 进度条塞在卡片底部，密度够但略拥挤——
新方案建议：**进度条贴底 2px + 只在有进度时显示状态点**，文字标签只留在详情页。

## 八、性能预算（验收标准）

| 指标 | 目标 | 测量方式 |
|------|------|----------|
| 冷启动到可交互 | < 1.5 s | 秒表 |
| 空闲内存（无播放） | < 120 MB | 任务管理器 |
| 播放中内存 | < 180 MB | 同上 |
| 安装包体积 | < 15 MB | 产物大小 |
| 安装后磁盘占用 | < 50 MB | 同上 |
| 1 万集列表滚动 | 稳定 60 fps | DevTools performance |
| 订阅 20 个频道刷新 | < 15 s（并发 3） | 日志计时 |

**长列表必须虚拟滚动**：Svelte 用 `@tanstack/svelte-virtual` 或自己写窗口化。
参考实现用 Compose 的 LazyColumn 天然虚拟化，Web 侧要自己做。

## 九、打包与分发

| 平台 | 方案 | 说明 |
|------|------|------|
| Windows | **NSIS**（Tauri 默认） | 比 MSI 小，内置 updater 支持 |
| macOS（预留） | `.dmg` + 公证 | 需要 Apple 开发者账号（$99/年） |

**自动更新**：`tauri-plugin-updater` + GitHub Releases。
开源 + GitHub 托管的情况下这条路最顺，不需要自建更新服务器。

**签名**：Windows 代码签名证书可选（约 $100–300/年）。
不签名的话首次运行会被 SmartScreen 拦一次，个人自用可接受。

## 十、里程碑细化

| 阶段 | 内容 | 验收 | 人日 |
|------|------|------|------|
| **M0 原型** | Tauri 空壳 + 手输 RSS + 播放一集 + 打包出 exe | 双击能装、能播、能听到声音 | 3–5 |

| **M3 订阅与发现** | 刷新并发、榜单、搜索、OPML | 20 个频道 15 秒内刷完 | 8–10 |
| **M4 资料库** | 历史、收藏、下载（续传+限速） | 断网重连能续传 | 6–8 |
| **M5 打磨发布** | 托盘、媒体键、通知、自动更新、UI polish | 五项性能预算达标 | 8–10 |
| 合计 | | | **37–50 人日** |

比之前的 71–102 人日估算少，原因是：Web 前端做 UI 效率明显高于 Compose，
且砍掉了"学 JVM 打包"这条弯路。

这两个是本方案最大的两个未知数。

## 十一、风险与缓解

| 风险 | 可能性 | 影响 | 缓解 |
|------|--------|------|------|
| WebView2 音频格式兼容不足 | 低 | 高 | M0 阶段就用真实播客源测 5 个以上不同编码 |
| 后台播放被 WebView 挂起 | 中 | 高 | M0 就测最小化到托盘后继续播放 |
| 长列表性能不达标 | 中 | 中 | 虚拟滚动 + 封面懒加载；M3 前压测 5000 条 |
| Rust 学习曲线拖慢进度 | 中 | 中 | 后端逻辑控制在一人可维护的复杂度；不确定处用简单方案 |
| WebView2 运行时缺失 | 低 | 中 | NSIS 安装包内置 WebView2 bootstrapper |
| 打包体积超预期 | 低 | 低 | 关掉 debug 符号、strip、opt-level=z |

## 十二、还需要你确认的细节

1. **视觉参考**：有想对标的客户端吗（小宇宙 / Spotify / Pocket Casts / Apple Podcasts）？
   不同参考的 UI 走向差别很大，越早定越好。
2. **中文内容源**：苹果 CN 区够用吗？如果必须覆盖某些平台独家的中文播客，
   那些没有公开 API，只能爬，有合规风险——需要你明确。
3. **自动更新**：要不要做？做的话发布渠道用 GitHub Releases 吗？
4. **数据迁移**：要不要把现在 Podara 里的订阅和收听进度导进来？
   （要做的话 M1 阶段加一个导入工具，约 3 天）
5. **是否接受 Rust**：如果完全不想碰 Rust，方案要退回 Flutter（代价是包体和内存翻倍）。
