### ⚠️ 关于许可证必须说清的一件事

你选了「开源」，但**开源和"能随便选协议"是两件事**。

参考实现是 **GPL-3.0**。新仓库是"看着它的代码重写一遍"，在著作权法意义上
极大概率被认定为**衍生作品**——AI 辅助重写不改变这一点（代码表达相同、结构相同、
表结构相同）。衍生作品的传染性意味着：**新仓库只能用 GPL-3.0（或兼容协议）发布**。

现实建议：

- **默认沿用 GPL-3.0** —— 零风险，且和你"开源"的意向一致。
- 想做 MIT / Apache-2.0，前提是**完全独立实现**（不看原码、不复制表结构、
  不复制命名），这在当前语境下不现实，等于放弃 90% 的参考价值。
- 最坏情况：如果你以后想做成闭源商业产品，**这条路线是堵死的**（GPL 不允许）。
  真想商业化，就得从"参考它的产品思路、自己写实现"起步，而不是"重写它的代码"。

> 这条不影响现在开工，但请在 M0 之前想清楚，因为 license 文件一旦发布就很难改。

## 一、技术栈定稿

| 层 | 选型 | 说明 |
|----|------|------|
| 应用壳 | **Tauri 2** | 用系统 WebView2，不自带浏览器 |
| 前端框架 | **Svelte 5** | 运行时几 KB，比 React 轻一个量级；runes 状态模型够用 |
| 构建 | **Vite 6** | 冷启动构建快 |
| 样式 | **Tailwind CSS 4** | 编译期生成，运行时零开销 |
| 语言（前端） | TypeScript | — |
| 语言（后端） | Rust（stable） | 网络、解析、DB、下载、系统集成 |
| 数据库 | **SQLite** + `rusqlite` | 单文件、零配置、可控 |
| 迁移 | 自建 `schema_version` 表 | 简单场景不必上 diesel/sqlx migrate |
| 异步运行时 | `tokio` | reqwest 依赖它 |
| HTTP | `reqwest`（rustls） | 比 openssl 省依赖、编译快 |
| RSS 解析 | `feed-rs` | 处理 RSS/Atom/命名空间 |
| 序列化 | `serde` / `serde_json` | — |
| 日志 | `tracing` + 文件轮转 | — |
| 错误 | `thiserror`（库）+ `anyhow`（应用层） | — |
| 测试 | `cargo test` + `vitest` | — |

**刻意不引入的东西**（为了轻量）：

- 不要 ORM（diesel/sea-orm）——12 张表手写 SQL 完全可控，且避免编译期膨胀
- 不要 UI 组件大礼包（MUI/Ant）——手写 + Tailwind，样式才跟得上审美要求
- 不要状态管理库（Redux/Zustand）——Svelte 5 的 runes 原生够用
- 不要动画库（Framer Motion 等）——Svelte 内置 transition 足够且更轻

## 二、进程架构

```
┌─────────────────────────────────────────┐
│  WebView2（Svelte UI，负责渲染与交互）    │
│  · 页面、组件、动画                      │
│  · <audio> 元素持有播放状态              │
└──────────────┬──────────────────────────┘
               │ IPC：invoke（前端调用）+ emit（后端推送）
┌──────────────┴──────────────────────────┐
│  Rust Core（负责一切"重活"）             │
│  · reqwest 抓 RSS / 调 API               │
│  · feed-rs 解析                          │
│  · SQLite 读写                           │
│  · 下载（断点续传、限速）                 │
│  · 托盘 / 全局媒体键 / 通知 / 单实例      │
└─────────────────────────────────────────┘
```

**职责边界（硬约束）**：

| 事情 | 谁做 | 为什么 |
|------|------|--------|
| 抓 RSS、解析 XML | Rust | 大文件、CPU 密集，别放 WebView |
| 所有 SQL | Rust | 前端不许碰数据库 |
| 下载与限速 | Rust | 需要精确控制并发与限速 |
| 播放控制、进度 | **前端 `<audio>`** | 与 UI 天然同步，省一层 IPC 延迟 |
| 进度落库 | 前端节流后 invoke → Rust | 避免每次 timeupdate 都跨进程 |
| 全局媒体键 | Rust 监听 → emit 给前端 | 前端执行实际播放控制 |

## 三、音频方案（最容易翻车的地方）

### 3.1 主方案：HTML5 `<audio>`

WebView2 就是 Chromium，`<audio>` 支持的正是播客常用格式：
MP3、AAC/M4A、OGG/Opus、FLAC、WAV。

**能满足的需求**：

| 需求 | 实现 |
|------|------|
| 播放/暂停/seek | 原生 |
| 倍速 0.5–3.0，变速不变调 | `audio.playbackRate`（Chromium 内置时间伸缩） |
| 音量 | `audio.volume` |
| 进度事件 | `timeupdate`（约 4Hz，够用） |
| 睡眠定时 | `setTimeout` + `pause()` |
| 章节跳转 | `audio.currentTime = chapter.start` |
| 音量增强（>100%） | **WebAudio**：`createMediaElementSource` + `GainNode` |

**要求服务器支持 Range**：播客 CDN 基本都支持，否则 seek 会重下整个文件。
降级：检测到不支持就整集下载到本地再播。

### 3.2 三个必须提前处理的问题

**问题一：后台定时器被节流。**
WebView2 在窗口隐藏时会节流 JS 定时器（可能降到 1 次/秒甚至更低）。
- 播放本身不受影响（有音频输出时 Chromium 不会挂起）
- 但 `setTimeout` 驱动的进度上报会变慢
- **对策**：进度上报挂在 `timeupdate` 事件上（事件驱动不受定时器节流影响），
  再用 Rust 侧的定时器做兜底（每 5 秒向库里 flush 一次）

**问题二：窗口隐藏后音频可能被中断。**
最小化到托盘时如果用 `window.close()` 会销毁 WebView。
- **对策**：托盘最小化要用 `window.hide()`，不要 destory；退出才销毁

**问题三：格式兼容的边缘情况。**
个别播客用 ALAC、或者 MP3 里塞了奇怪的 ID3。
- **对策**：预留 `PlaybackBackend` 接口，Rust 侧可接 `symphonia + cpal` 兜底（V2 再做）

### 3.3 为什么不自己写音频引擎

参考实现自己写了 libmpv 的 JNA 绑定，代价是：
20MB DLL、一堆 FFI 坑（`WPARAM` 宽度问题就调了很久）、跨平台要各带一份。

播客只需要"能播 + 能变速"，Chromium 已经做得很好。
**把自研精力花在推荐、章节解析、同步上，比花在解码器上划算得多。**

### 4.2 核心表 DDL 草案

```sql
-- 播客（一条记录 = 一个订阅，订阅关系就是这个表，不另设 subscription 关系表）
CREATE TABLE podcast (
  origin          TEXT PRIMARY KEY,    -- RSS URL，天然去重
  title           TEXT NOT NULL,
  custom_title    TEXT DEFAULT '',     -- 用户手动改名，非空时优先展示
  author          TEXT,
  description     TEXT,
  image_url       TEXT,
  link            TEXT,
  language        TEXT,
  seed_color      INTEGER,             -- 封面取色，0/NULL 表示未取
  source          TEXT DEFAULT 'rss',  -- rss / apple / podcastindex（仅记录来路）
  skip_intro_sec  INTEGER DEFAULT 0,   -- 跳过片头，沿用参考实现的实用功能
  skip_outro_sec  INTEGER DEFAULT 0,   -- 跳过片尾
  created_at      INTEGER NOT NULL
);

-- 单集
CREATE TABLE episode (
  id             TEXT PRIMARY KEY,     -- 沿用参考实现规则：{feedUrl}:{episodeUrl} 或 guid
  guid           TEXT,                 -- RSS 原始 guid，刷新去重的真正依据
  origin         TEXT NOT NULL REFERENCES podcast(origin) ON DELETE CASCADE,
  title          TEXT NOT NULL,
  description    TEXT,
  link           TEXT,                 -- 单集网页地址
  author         TEXT,                 -- 单集级作者，可空
  audio_url      TEXT NOT NULL,
  image_url      TEXT,
  pub_date       INTEGER NOT NULL,
  duration_ms    INTEGER DEFAULT 0,    -- ⚠️ 毫秒。RSS 里是 "HH:MM:SS"，入库前 ×1000
  is_new         INTEGER DEFAULT 0,
  chapters_url   TEXT,                 -- <podcast:chapters>
  transcript_url TEXT                  -- <podcast:transcript>
);
CREATE INDEX idx_episode_origin_pub ON episode(origin, pub_date DESC);
CREATE INDEX idx_episode_guid ON episode(origin, guid);
CREATE INDEX idx_episode_new ON episode(is_new) WHERE is_new = 1;

-- 播放进度
CREATE TABLE play_state (
  episode_id    TEXT PRIMARY KEY REFERENCES episode(id) ON DELETE CASCADE,
  position_ms   INTEGER NOT NULL DEFAULT 0,
  duration_ms   INTEGER NOT NULL DEFAULT 0,
  finished      INTEGER NOT NULL DEFAULT 0,   -- 粘性：>98% 置 1，永不回退
  updated_at    INTEGER NOT NULL
);

-- 收藏 / 历史（不砍成字段：需要独立的时间排序，且要能留在"孤儿集"上）
CREATE TABLE favorite (
  episode_id  TEXT PRIMARY KEY REFERENCES episode(id) ON DELETE CASCADE,
  added_at    INTEGER NOT NULL
);
CREATE TABLE history (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  episode_id  TEXT NOT NULL,
  origin      TEXT NOT NULL,
  played_at   INTEGER NOT NULL
);
CREATE INDEX idx_history_time ON history(played_at DESC);

-- 订阅的可选配置 + 增量抓取缓存（和 podcast 是一对一，独立表只为了不污染主表）
CREATE TABLE subscription (
  origin         TEXT PRIMARY KEY REFERENCES podcast(origin) ON DELETE CASCADE,
  notify_new     INTEGER DEFAULT 1,
  auto_download  INTEGER DEFAULT 0,
  etag           TEXT DEFAULT '',
  last_modified  TEXT DEFAULT '',
  content_length TEXT DEFAULT '',
  last_checked   INTEGER DEFAULT 0,
  new_count      INTEGER DEFAULT 0
);

-- 下载任务
CREATE TABLE download_task (
  episode_id    TEXT PRIMARY KEY REFERENCES episode(id) ON DELETE CASCADE,
  origin        TEXT NOT NULL,
  file_name     TEXT,                   -- 只存文件名，不存绝对路径（换机器/换目录能活）
  received      INTEGER DEFAULT 0,
  total         INTEGER DEFAULT 0,
  status        TEXT NOT NULL,          -- pending/downloading/paused/done/failed
  error         TEXT,
  updated_at    INTEGER NOT NULL
);

-- 播放会话（重启恢复）
CREATE TABLE player_session (
  id              INTEGER PRIMARY KEY CHECK (id = 1),
  current_episode TEXT,
  position_ms     INTEGER DEFAULT 0,
  speed           REAL DEFAULT 1.0,
  volume          INTEGER DEFAULT 100,
  updated_at      INTEGER
);

-- 播放队列（顺序即 id 顺序）
-- ⚠️ episode_id 必须可空：用户会往队列里塞裸音频 URL（实测老库里有喜马拉雅直链）
CREATE TABLE queue_item (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  episode_id  TEXT REFERENCES episode(id) ON DELETE CASCADE,
  raw_url     TEXT,                     -- episode_id 为空时的兜底
  title       TEXT,
  added_at    INTEGER NOT NULL
);
```

**必须开外键约束**：

```sql
PRAGMA foreign_keys = ON;   -- 每个连接都要执行，SQLite 默认是关的
```

参考实现就是因为没开、也没写 `ON DELETE CASCADE`，实测库里攒了
**1065 条指向已删除单集的孤儿进度记录**（5493 条进度 vs 4430 条单集）。
新库在设计阶段就用外键解决，而不是靠代码里手动清理。

**关于参考实现的 12 张表**：`podcastDownload` / `downloadTask` 合成一张
`download_task` 就够（完成态和进行态是同一件事的不同 status）；
`podcastItunesLookup` / `syncAction` 直接丢弃（前者是新库内存缓存的事，
后者是没做完的半成品）。净结果是 12 张 → 9 张，职责更清楚。

## 六、关键流程

### 6.1 订阅刷新（并发控制是重点）

```
前端触发 refresh
  → Rust: 读 subscription 表，筛出 last_checked 超过 10 分钟的
  → 用 Semaphore(3) 限制并发，逐个：
      GET feedUrl
        If-None-Match: <etag>
        If-Modified-Since: <last_modified>
      ├─ 304 → 跳过（不解析，省 CPU）
      └─ 200 → feed-rs 解析 → 与库中 guid 比对 → 新集 is_new=1
                → 更新 etag/last_modified/last_checked
  → emit listen-progress 推进度
  → 返回 { new_episodes, not_modified }
```

**首次抓取特殊处理**：库里没有该 origin 的任何单集时，全部入库但 **is_new=0**
（当作基线，避免一次冒出几百条未读）。这一条是参考实现踩坑后才加的。

**清理策略（很重要，替代老实现的"删了就算"）**：

刷新后清理过期单集时，**以下三类绝不删除，只更新**：

1. 被收藏的（`favorite` 里有记录）
2. 有播放进度的（`play_state.position_ms > 0` 或 `finished = 1`）
3. 在播放队列里的（`queue_item` 里有记录）

其余只保留该 feed 最新的 N 条（默认 300，可配置），避免库无限膨胀。
老实现没有这个策略，直接导致 1065 条孤儿进度记录（见 13.2 陷阱二）。

### 6.2 播放与进度

```
用户点某集
  → 前端: audio.src = url; audio.playbackRate = 用户设置; audio.play()
  → 前端: 从 progress_get 拿到 position，audio.currentTime = position
  → audio.ontimeupdate（约 4Hz）
      → 更新 UI 进度条（纯前端，无 IPC）
      → 每 5 秒节流一次：progress_save(episode_id, pos, dur)
  → 暂停/切集/退出：立即 flush 一次

finished 判定：
  前端计算 pos/dur > 0.98 → invoke progress_finish(episode_id)
  → Rust 置 finished=1（粘性，重听也不回退）
```

**为什么 finished 要粘性**：用户听完一集后再重听，不该被打回"未听完"。
参考实现已经这么做了（`EpisodeProgress.finished` 一旦置位不再清除）。

### 6.3 下载

```
download_start(episode_id)
  → Rust: 建 download_task(status=pending)
  → 检查是否有断点（task.received > 0）
  → GET Range: bytes=<received>-
      ├─ 206 → 追加写入
      └─ 200 → 服务端不支持续传，删文件重下
  → 流式写入 + 令牌桶限速（用 tokio 的 interval 控制节奏）
  → 每 500ms emit download-progress
  → 完成：改文件名为最终名，status=done，写 play_state 的本地路径
```

## 七、内容源策略（RSS-first）

### 7.1 定位：核心能力不依赖任何目录服务

这是第 5 条决策的技术含义——**把"目录"降级成可选增强，而不是命脉**。

```
必须永远可用（不依赖任何第三方 API）：
  粘贴 RSS 链接订阅 ──→ 抓取 ──→ 解析 ──→ 入库 ──→ 播放
  
可选增强（挂了不影响主流程）：
  OPML 批量导入
  Apple 目录搜索 / 榜单 / 分类浏览
```

判定标准很简单：**把网线拔掉再插回来、把 Apple API 拉黑，应用还应该能完整用**。
这一条决定了架构——发现页必须能"降级为空入口"而不报错。

### 7.2 三条录入路径

| 路径 | 场景 | 成本 |
|------|------|------|
| **粘贴 RSS 链接** | 知道节目地址（从任何地方看到） | 极低，M0 就要有 |
| **OPML 导入** | 从别的播客客户端搬家 | 低，M3 |
| **目录搜索/榜单** | 不知道地址，想逛 | 中，M3 |

关键设计：**OPML 导入导出必须做**，且格式要兼容主流客户端（小宇宙、Pocket Casts、
Apple Podcasts 都能导 OPML）。这是"通用 RSS 客户端"最重要的护城河——
用户随时能走，才敢来。

### 7.3 Apple 目录的合规边界

只允许这些端点，全部是 Apple 官方公开、无需 key 的：

| 用途 | 端点 | 备注 |
|------|------|------|
| 搜索 | `itunes.apple.com/search?term=&media=podcast&country=cn` | 默认 `country=cn`（参考实现的 bug 就是这里默认了 US） |
| 详情 | `itunes.apple.com/lookup?id=<collectionId>&entity=podcast` | 拿 `feedUrl` |
| 榜单 | `itunes.apple.com/cn/rss/toppodcasts/limit=100/json` | 只取 id，再批量 lookup |
| 分类 | `itunes.apple.com/WebObjects/MZStoreServices.woa/ws/genres?id=26` | 播客类目树，**缓存到本地**，不要每次请求 |

**硬边界（写进 AGENTS.md，防止 AI 后来"顺手"越界）**：

- ✅ 只调上面这些官方端点，只取元数据（标题、作者、封面 URL、`feedUrl`、类目）
- ✅ 音频一律从节目自己的 RSS / CDN 拉，**不经过 Apple**
- ❌ 不爬任何网页（包括小宇宙、喜马拉雅、Apple 的网页版）
- ❌ 不逆向任何私有 API
- ❌ 不镜像 / 不转存节目内容
- ❌ 不做登录态抓取

**速率限制**：Apple 这个 API 大约 20 req/min/IP，超了会返回 403。
对策：搜索结果本地缓存 24 小时；榜单缓存 6 小时；详情按 `collectionId` 永久缓存
（`feedUrl` 基本不变）。缓存不落库，放内存 + 一个 `cache/apple.json` 就够。

### 7.4 小宇宙的内容怎么办——不需要抓它

实测你老库里的队列有这么一条：

```
episode_id : https://feed.xyzfm.space/l3gtny3n6ab7:6adf1a2ac96c8942ec1271a9
audio_url  : https://dts-api.xiaoyuzhoufm.com/track/6458ad1a306513184c5ea...
```

也就是说：**小宇宙的节目有公开的 RSS（`feed.xyzfm.space`），音频也走标准直链**。
你得出的"不抓第三方非官方接口"的结论是对的，而且**不会损失内容覆盖**——
用户照样能订阅小宇宙上的节目，只是入口是 RSS 而不是它的 App。

同类还有：`feed.xyzfm.space`（小宇宙托管）、`typlog.io`（少数派等）、
各类 `anchor.fm` / `fireside.fm` / `simplecast` / 自建 WordPress。
这些全部是标准 RSS，通用客户端天然覆盖。

**所以"内容源不足"这个担心，80% 是入口问题而不是供给问题。**
解决方案不是去爬，而是把"找到 RSS"这件事做顺：搜索做得准、OPML 能导、能粘贴。

### 7.5 发现页在没有推荐流时长什么样

小宇宙的发现页是编辑精选 + 推荐流，我们没有编辑、也没有行为数据。
**不要假装做一个劣质推荐**，改做三件确定性的事：

1. **分类浏览**（Apple 类目树 + 榜单）——"我想找商业类播客"这种明确需求
2. **搜索**（Apple 搜索 + 本地已订阅库搜索，两段合一）
3. **导入入口放显眼位置**——这是 RSS 客户端最重要的"发现"方式

**V1.5 可加的本地推荐**（完全离线、可解释，不需要平台数据）：

> 基于已订阅节目的类目分布做"猜你喜欢"——
> 比如你订阅了 8 个商业访谈类，就从 Apple 榜单的同类目里推荐 5 个未订阅的。
> 逻辑 50 行以内，可解释（"因为你订阅了 X"），不涉及任何隐私外传。

这比"硬套协同过滤"诚实得多，也符合"推荐算法"这个需求——
**能做的是可解释的相似推荐，做不了的是平台级个性化推荐**（没数据）。

## 八、UI 设计方向（小宇宙视觉语言）

### 8.1 先划清界限：抄什么，不抄什么

小宇宙是**移动端 + 有内容运营 + 有社区**的产品。直接照搬信息架构会做出一个
"功能不全的小宇宙"。正确做法是**只取视觉语言**：

| 维度 | 做法 | 理由 |
|------|------|------|
| 大封面、大留白 | ✅ 完整继承 | 这是它审美的主体，桌面端同样成立 |
| 圆角方形封面（非圆形） | ✅ 继承，10px | 圆形封面是 Spotify 语言，方形更"播客" |
| 克制的灰阶层级、几乎无投影 | ✅ 继承 | 桌面软件尤其忌讳重投影 |
| 暖色强调 + 可被封面主色覆盖 | ✅ 继承 | 进度条、选中态用它 |
| 单集条目「封面 + 标题 + 播客名 + 时长」四段式 | ✅ 继承 | 信息密度正好 |
| 底部 Tab 导航 | ❌ 改左侧图标栏 | 桌面端底部 tab 反人类 |
| 推荐信息流 / 编辑精选 | ❌ 无（见 7.5） | 没编辑、没数据，硬做只会难看 |
| 评论 / 时间戳弹幕 | ❌ V1 不做 | 需要服务端，与"单机 RSS 客户端"定位冲突 |
| 付费 / 赞赏 / 会员 | ❌ 不做 | 无商业模式 |
| 播放页大封面沉浸态 | ✅ **必做** | 桌面端最能出效果的一屏，也最能体现"审美到位" |

### 8.2 布局（桌面化改造）

```
┌────┬───────────────────────────────────────┬──────────┐
│ 图 │  页面标题          [搜索]      [排序]  │          │
│ 标 ├───────────────────────────────────────┤  队列抽屉 │
│ 栏 │                                       │  (320px) │
│    │                                       │  可折叠   │
│72px│           主内容区                     │          │
│    │     列表 / 卡片网格 / 详情              │          │
│    │                                       │          │
├────┴───────────────────────────────────────┴──────────┤
│ 播放条 68px： 封面▢ 标题/播客  ─────●────  1.5× ⏮⏯⏭ ♪  │
└───────────────────────────────────────────────────────┘
```

- **左侧图标栏 72px**：发现 / 订阅 / 资料库 / 设置，图标 + hover 出 tooltip。
  不做 220px 文字版——桌面播客应用的主内容是列表，横向空间要留给内容。
- **播放条 68px**：未播放时高度 0（不占位），首播时 slide-up 进入。
- **队列抽屉**：从播放条右侧展开，覆盖在内容上，不做独立页。
- **播放页**：点播放条封面 → 全屏沉浸态（不是新窗口，是覆盖层）。

### 8.3 六个页面

| 页面 | 关键元素 | 备注 |
|------|----------|------|
| **订阅（首页）** | 「最新更新」跨播客聚合流，按 `pub_date` 倒序；行内：48px 方封面 + 标题 + 播客名 · 相对时间 + 底部 2px 进度条 | 这是参考实现最好的一个改动，直接继承 |
| **发现** | 顶部搜索框 + 分类胶囊（Apple 类目）+ 榜单网格（`auto-fill` 最小 160px）+ **右上角"导入"按钮** | 导入入口必须显眼，见 7.5 |
| **频道详情** | 模糊封面背景（blur 60px, opacity 0.25）+ 160px 大封面 + 标题/作者/单集数 + 简介折叠 + 单集列表 + 「全部标为已播」 | 订阅按钮在右上角 |
| **播放页** | 全屏覆盖层：55vh 大封面 + 标题/播客 + 可拖进度条 + 章节列表（有 `<podcast:chapters>` 才显示）+ 「+30s / -15s」+ 底部控制排 | 小宇宙的招牌屏，MVP 必须有 |
| **资料库** | 三个分段：历史 / 收藏 / 下载（下载带进度与暂停） | 用分段控件而非三个导航项，减少层级 |
| **设置** | 播放（默认倍速、跳过片头尾、音量增强）、订阅（并发、通知、自动下载）、存储（下载目录、清理）、关于（版本、更新、导入旧数据） | 「导入旧数据」放这里，见第十三章 |

### 8.4 设计 Token

| 项 | 浅色 | 深色 |
|----|------|------|
| 背景 | `#FAFAFA` | `#0F0F11` |
| 卡片/浮层 | `#FFFFFF` | `#17171A` |
| 文字主 | `#16161A` | `#F2F2F3` |
| 文字次 | `#8A8A8E` | `#8A8A8E` |
| 文字三级 | `#B4B4B8` | `#5C5C61` |
| 分隔线 | `rgba(0,0,0,.06)` | `rgba(255,255,255,.08)` |
| 强调色 | `#FF5C33`（可被封面主色覆盖） | 同 |

| 项 | 值 |
|----|-----|
| 圆角 | 封面 10px / 卡片 14px / 按钮 999px（胶囊）/ 输入框 10px |
| 字号 | 页面标题 20/600 · 区块标题 15/600 · 列表标题 14.5/500 · 正文 13.5/400 · 次要 12/400 |
| 行高 | 1.45（中文需要比英文更宽） |
| 字体栈 | `PingFang SC, Microsoft YaHei UI, Segoe UI Variable, system-ui, sans-serif` |
| 间距 | 4px 基数，常用 8 / 12 / 16 / 24 / 32 |
| 阴影 | **全面禁用**，只用 1px 描边 + 背景色差分层 |

**明暗双主题 V1 就要做** —— Token 化之后这件事成本接近于零，事后补才贵。

### 8.5 动效（克制，但要有）

| 场景 | 动效 |
|------|------|
| 列表项入场 | stagger 25ms，`fly(8px) + fade`，180ms，ease-out |
| 播放条升起 | height 0→68px + fade，220ms |
| 播放条 → 播放页 | 封面共享元素过渡 320ms（Svelte `crossfade`） |
| 进度条数值 | `width` 120ms linear（必须跟手，不能有迟滞感） |
| 抽屉 | `fly(x: 100%)` 240ms |

**明确禁止**：弹跳效果、超过 350ms 的过渡、同屏 3 个以上元素同时动、
任何"loading 转圈超过 300ms 还没内容"的地方（用骨架屏）。

### 8.6 信息密度

参考实现被吐槽的点是**卡片底部塞了状态标签 + 进度条，一行里信息过载**。
新方案的单集行（高 64px）：

```
┌──────┐  从"看不懂"到浮亏18亿还要加仓，段永平到底在买什么？      ← 14.5/500，超出省略
│ ▢48  │  十字路口Crossing · 1小时26分 · 3天前                 ← 12/400，次级色
│      │  ▔▔▔▔▔▔▔▔▔▔▔▔░░░░░░░░░░░░░░░░░░░░                    ← 有进度才显示，2px
└──────┘
```

- 进度条贴底 2px，**只在 `position_ms > 0` 时渲染**
- 已完播：不显示进度条，在标题右侧放一个 14px 的 ✓（三级色）
- 时长格式化：`< 1h` → `26分`，`>= 1h` → `1小时26分`
- 相对时间：7 天内用"3天前"，更早用"10月19日"

| 合计 | | | **40–55 人日** |

比 `新仓库开发方案.md` 里的 71–102 人日少，原因是：Web 前端做 UI 明显快于 Compose，

**推进节奏的三条硬规矩**：

1. **M0 不做完不许往下走**。它验证的是本方案两个最大未知数：音频能不能播、

2. **M1 的导入工具要早做**（第 2 天就能写），因为它是你"能不能切开旧应用"的开关。

3. **M3 之后才开始做视觉打磨**。前面几个阶段用丑陋但可用的界面推进，
   不要在前端样式上来回改——那是 M5 的事。

## 十二、风险与缓解

| 风险 | 可能性 | 影响 | 缓解 |
|------|--------|------|------|
| WebView2 音频格式兼容不足 | 低 | 高 | M0 阶段用真实播客源测 5 种以上不同编码（mp3/aac/m4a/ogg/flac） |
| 后台播放被 WebView 挂起 | 中 | 高 | M0 就测"最小化到托盘 10 分钟后还在播" |
| 长列表性能不达标 | 中 | 中 | 虚拟滚动 + 封面懒加载；M3 前压测 5000 条 |
| Rust 学习曲线拖慢进度 | 中 | 中 | 后端控制在一人可维护复杂度；拿不准的地方选最笨的写法 |
| WebView2 运行时缺失 | 低 | 中 | NSIS 内置 WebView2 bootstrapper |
| 打包体积超预期 | 低 | 低 | `opt-level="z"`、strip、`panic="abort"` |
| **Apple API 变更 / 限流** | 中 | **低** | RSS-first 架构保证核心可用；发现页可降级为空入口（见 7.1） |
| **GPL 传染导致无法闭源商用** | 中 | **高** | 见第零章警告；要商用就别沿用原码结构 |
| **导入旧数据出错** | 低 | 高 | 只读打开 + dry-run 报告 + 单事务 + 校验行数（见第十三章） |
| 自己维护动力不足（自用项目最大风险） | **高** | **高** | M0/M1 快速做出"能日常用"的版本，先接管自己的收听，再谈完善 |

最后一条是真实风险，不是凑数：参考实现有 5 个未合并的功能分支、
一堆半成品字段（`enableNotifications` / `Genre` 枚举 / `SyncManager`），
就是"做了一半没继续"的痕迹。**新仓库要警惕同样的轨迹**——
宁可 M0–M2 做得窄，也要先做到每天愿意打开它。

## 十三、旧数据迁移（已实测老库）

### 13.1 老库的真实状态

先看清楚要迁什么。以下是 2026-10-27 对你本机 `C:\Users\ez\.podara\podara.db`
（38.5 MB）的实测统计：

| 老表 | 行数 | 真正有价值的数据 | 处理 |
|------|------|------------------|------|
| `podcast` | 21 | **这就是订阅列表**（21 个中文播客） | 全迁 |
| `podcastEpisode` | 4430 | 全部 | 全迁（description 是大头，38MB 的主要来源） |
| `podcastEpisodePlayState` | 5493 | **只有 5 条有真实进度，0 条 finished** | 只迁 `position_ms > 0` 的 |
| `podcastSubscription` | **0** | 空表 | 跳过（订阅关系不在这一层） |
| `podcastFavorite` | 0 | 空 | 跳过 |
| `podcastHistory` | 14 | 14 条 | 全迁 |
| `podcastDownload` | 0 | 空 | 跳过 |
| `downloadTask` | 0 | 空 | 跳过 |
| `podcastItunesLookup` | 1 | 无价值 | 丢弃 |
| `syncAction` | 0 | 半成品 | 丢弃 |
| `playerSession` | 1 | 当前播放位置 260208 ms | 迁 |
| `playerQueueItem` | 3 | 3 条队列（含 1 条喜马拉雅裸 URL） | 迁 |

**结论：要迁的数据量小到可以忽略**（21 + 5 + 14 + 3 + 1 条核心数据）。
所以 M1 的导入工具**技术难度低、风险低**，3 人日的估算主要花在
dry-run 报告、孤儿处理、边界校验上，不是花在数据量上。

### 13.2 五个必须处理的陷阱

**陷阱一：`duration` 单位不一致（最危险）。**

```
podcastEpisode.duration          → 秒    （RssConverter.parseDuration 从 "1:26:54" 算出 5214）
podcastEpisodePlayState.durationMs → 毫秒  （播放器上报的是毫秒）
```

新库统一用 `duration_ms`。迁移时 **`episode.duration × 1000`**，
`playState.durationMs` 原样。写错这一步，所有进度条会变成 1/1000 或 1000 倍。

**陷阱二：1065 条孤儿进度记录。**

`playState` 5493 条 vs `episode` 4430 条，差值全是已删单集残留的进度行。
迁移时 `JOIN episode` 过滤即可，但**要计数并写进报告**——
如果孤儿数异常多，说明老库的清理逻辑有问题，值得顺手修掉。

**陷阱三：`podcastSubscription` 是空表。**

订阅关系实际以 `podcast` 表有没有这条记录为准，`podcastSubscription` 只承载
「通知/自动下载/ETag 缓存」这些可选配置。所以：
**迁订阅 = 迁 `podcast` 表**，别去 `podcastSubscription` 里找。

**陷阱四：队列里有裸 URL 条目。**

实测队列第 0 条是 `episodeId = 'xmly_track_1027807155'`（喜马拉雅），
在 `episode` 表里**根本不存在**。所以新库的 `queue_item.episode_id`
必须允许为空，并用 `raw_url` 兜底（DDL 里已经这么设计了）。

另外：这类第三方直链带签名参数，**大概率已经失效**。迁移时保留但标记，
播放失败就让用户删掉，不要因为一条坏 URL 让整个队列报错。

**陷阱五：收藏/历史的"孤儿"问题（本机未触发，但设计上要防）。**

老实现把整集快照冗余存进 `podcastFavorite`（title/audioUrl/duration 全存一份），
就是为了防"集被刷新删掉后收藏失效"。
新库用外键 + **保留策略**替代冗余：刷新时对「被收藏 / 有进度 / 在队列里」的集
**不执行删除**，只更新。这样既不用存快照，也不会丢数据。

### 13.4 工具形态与安全要求

**形态**：设置页 →「存储」→「从旧版 Podara 导入」。不做命令行工具，
因为你自己就是用户，图形化更愿意用。

**五条安全要求**（缺一条就不要写代码）：

1. **只读打开旧库**：`file:...podara.db?mode=ro&immutable=1`，物理上不可能写坏它。
2. **先 dry-run，后执行**：点「导入」先跑一遍只读扫描，弹出报告——
   ```
   将导入：订阅 21 · 单集 4430 · 进度 5 · 历史 14 · 队列 3
   将跳过：孤儿进度 1065 · 空进度 5488 · 失效直链 0
   目标库已有数据 0 条，可安全导入
   ```
   确认后才写。
3. **单事务写入**：整个导入在一个事务里，任何一步失败全部回滚。
4. **冲突策略**：目标库非空时，按 `origin`/`id` 做 upsert，
   **新库有进度时以新库为准**（不能用旧数据覆盖你新听的）。
5. **留报告**：导入完成后写 `import-report.json` 到数据目录，
   记录各表导入/跳过条数与所有异常行，出问题能追溯。

**不做的**：不做反向导出（新库→旧库格式），没意义；
不做增量同步（两边同时用），会带来双向冲突，得不偿失。
